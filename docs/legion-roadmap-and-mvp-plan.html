1. Product, flow, and data in plain English

The product

You talk to Legion about an outcome. Legion uses the selected repository’s instructions and approved knowledge to ask useful questions. You confirm one exact specification. Your local Worker runs Legion with your local tools and provider accounts, producing an isolated candidate plus checks and independent review. Your phone can show progress and the result. Applying code remains a separate local action.

The shared-intelligence ambition is durable continuity across projects: Legion remembers approved decisions, understands relevant relationships, coordinates specialists, and improves from verified outcomes. It is broader than a coding launcher, but coding is the first buildable product.

4. One orchestrator, replaceable participants

Core and orchestrator

Domain-neutral contracts, reducers, routing, work graph, validation, review, evidence and convergence. Standalone local mode owns a local ledger. A cloud Job uses the Hub ledger and a fenced local runner; imported local work is a new explicitly linked record, never an automatic dual-master merge.

Cloud Hub

One optional customer-hostable application for identity, sessions, confirmations, queue, safe evidence, knowledge and audit. It runs ordinary service code but no model inference, coding harness, repository tests or arbitrary task commands in MVP.

Worker and Capacity

Worker polls outward, verifies authority, journals work and invokes existing Legion. Capacity is where execution happens and who owns credentials. MVP selects one enrolled local binding per Job; later capacities add location choices through the same contract.

Provider and role

Provider is the execution adapter; model is its underlying reasoning service. Planner, implementer and reviewer are bounded role instances. The orchestrator is a state owner, not a permanently privileged model personality.

Project Agent and Ability

An Agent manifest references repository instructions, allowed domain plugins/tools, namespaces, validators and limits. An Ability has typed input/output, effect class, authority, timeout and recovery. Domain behavior belongs outside Core.

Knowledge and cognition

Sources remain authoritative. A Ledger records attributed assertions; disposable graph projections support retrieval; Context Packs select bounded facts. Later cognitive components advise selection behind the same policy and proof boundaries.

Dependency direction: versioned contracts → Core/local adapters; Hub and Worker adapters consume those contracts. Core imports no Hub infrastructure. Extend current state resolver, executor registry, run lifecycle, learning-context compiler, supervisor and convergence controller rather than creating parallel implementations.

One integration owner: each Job designates one integration Capacity. Parallel slices produce isolated candidates; authorized implementer roles compose them there. Independent review examines the exact integrated candidate and all authoring provenance. No fixed model owns integration forever.

6. P0 — Stabilize contracts and measure the baseline

Goal: make identity, authority and proof explicit before adding a networked product. Prerequisites: pinned v0.29.1 source and runnable current checks; diagnose any doctor failure from its recorded cause before another heavy run. Estimate: 2–4 engineer-weeks.

Capabilities: versioned semantic contracts, Provider/Capacity distinction, per-invocation reporting, known privacy classes and repeatable baseline measurements.

  1. Inventory current artifacts and failure paths; capture golden runs and existing fallback/review behavior. Record the exact version and source SHA.
  2. Define shared schemas/reducers/digest fixtures for sessions, Specs, Agents, clarification, Jobs, Attempts, invocations, results, approvals, knowledge and Context Packs. Keep reserved future Goal/cognitive types out of MVP implementation.
  3. Add Provider/Capacity identities additively; preserve executor compatibility at ingress. Reuse the canonical model/registry reader and remove duplicate catalog logic only with parity fixtures.
  4. Implement the pinned role-policy boundary from §3, first in observe mode, then opt-in enforcement. Policy promotion is a separate measured behavior change.
  5. Classify fields for Hub sync and training independently; default both to deny. Add bounded retention and local privacy fixtures. Plan accurate cloud-optional enterprise copy and a claims-to-evidence registry.
  6. Run compatibility, schema, privacy, mismatch/unknown identity and role-independence tests; record startup, context, run quality, cost and latency baselines.

Completion evidence: current shell/Python suites and doctor green or a resolved, documented prerequisite; cross-language canonical bytes agree; all primary/delegated policy paths covered; unknown assurance blocks where required; no model migration inferred from the document. Proposed claims checks must be implemented before advertised as existing doctor commands.

Rollback: disable new admission policy and shadow contracts, restore the recorded previous routing profile; retain additive receipts. Do not rewrite historic evidence. State after: current local execution is contract-stable and measurable. Example: the same bug fix now records Terra as author, the actual independent reviewer, their requested/effective assurance, and the local Capacity without changing the user’s checkout.

7. P1 — A complete local Project Agent

Goal: turn a request into an isolated, verified candidate from one local session. Prerequisites: P0 contracts, policy and baseline. Estimate: 5–8 engineer-weeks.

Capabilities: repository-owned Agent, durable work session, immutable Spec versions, structured questions, confirmed execution, resumability and safe projection in shadow mode.

  1. Implement Agent manifest loading over existing TOML/domain-plugin machinery; resolve instructions/tools/validators locally and pin the semantic manifest.
  2. Add the local work-session journal and Spec ledger. Keep detailed execution logs private and separate.
  3. Run deterministic required-field checks before a read-only clarification model call. Return bounded questions, a proposed Spec and a locally resolved base SHA.
  4. Require exact confirmation, then compile the plan into current plan/slices contracts. Use the pinned role policy, bounded fan-out and one integration worktree.
  5. Run validation and independent review against the final candidate; emit a terminal result with evidence. Stop code-changing work at review-ready.
  6. Resume from stage receipts and snapshots, reconciling uncertain work. Build the projector/cache/outbox with transport disabled.

Completion evidence: feature, bug, refactor and test-hardening examples; incomplete input yields questions and no code-changing invocation; kill/restart at each boundary; main checkout unchanged; strict review identity checks; repeated unchanged failure converges; terminal learning attempted without turning failure into success.

Rollback: switch off first-party sessions/planning and use existing explicit plan/slices workflows; preserve journals and candidates. State after: a useful local product exists before cloud work begins. Example: “add CSV export” becomes questions about columns and limits, a confirmed Spec, an isolated implementation and review-ready evidence. No domain app is required.

8. P2 — Hybrid Cloud MVP

Goal: continue a personal Legion session across devices while execution stays on an enrolled local machine. Prerequisites: P1 vertical slice and network-disabled projector tests. Estimate: 8–12 engineer-weeks plus pilot; full LLS is §§15–24.

Capabilities: one hostable Hub + Postgres, login/devices, logical repository and Agent identity, cloud messages/Specs, separate clarification requests, durable Jobs, safe results, approved knowledge and one active Job per Worker.

  1. Deploy the modular application and database; add identity, encrypted content, audit, retention and opaque bindings.
  2. Expose safe Agent metadata and cloud sessions. The UI shows missing/offline Workers before promising a response.
  3. Let outbound Workers claim structured read-only clarification requests; answers create new Spec versions. Only exact confirmation creates an execution Job.
  4. Deliver Jobs through durable claims, fenced leases, supervised local execution, cancellation and evidence reconciliation.
  5. Add the typed Knowledge Ledger and two-device convergence. Keep empty-Ledger execution valid; enable Ledger context only after privacy/provenance and usefulness gates.
  6. Run load, outage, deletion, backup/restore, provider-policy and end-to-end parity tests; pilot one repo before adding a second device.

Completion evidence: phone → local clarification → confirmation → local execution → cloud review-ready; no Hub provider calls or repository credentials; crash suite prevents blind duplicate starts; stale content cannot enter a changed Spec; two devices agree on approved Ledger revisions; local non-model operations work without network and local provider-backed work works during a Hub-only outage.

Rollback: stop new cloud claims, drain/reconcile in-flight work, disable cloud context/sync independently and return to P1. Keep local candidates and outbox records until explicitly disposed. State after: cloud continuity and remote initiation, with local control of code. Example: a phone requests CSV export; a desktop Worker asks about encoding, executes only the confirmed answer, and returns a safe result. The phone cannot apply it.

9. P3 — Federated Knowledge Fabric

Goal: retrieve relationships and evidence across authorized sources without copying everything into a model. Prerequisites: P2 identity/Ledger/context boundaries. No C stage required. Estimate: 6–10 engineer-weeks.

Capabilities: typed entities/relations, source adapters, explicit expiring grants, bounded retrieval and disposable graph projections.

10. P4 — Multiple capacities, then isolated cloud execution

Goal: run the same proof contract on explicit additional machines. Prerequisites: P3 release and P2 recovery/identity gates; provider and data authority for each new location. No C stage required. Estimate: 8–14 engineer-weeks.

Capabilities: trusted capacity enrollment, explicit placement, runtime adapter parity, short-lived credentials and isolated remote slices.

  1. Enroll at least three independently identified capacities with trust class, ownership, approved Providers, budgets and concurrency.
  2. Run the local Worker contract suite against customer-managed machines; measure placement in observe mode.
  3. Evaluate isolated runtime alternatives using the hosting/runtime decision matrix; pin images, egress, secrets and lifetime assumptions.
  4. Ship remote read-only scouting/review first, then sandboxed test execution, bounded implementation and complete remote Jobs. Test commands can write fixtures, caches and artifacts or launch subprocesses; they require their own bounded execution permissions and are not classified as read-only. Use one isolated workspace per attempt/principal.
  5. Keep one integration Capacity and explicit approval for any later external publication. Add ambiguous-effect lookup/reconciliation for each publisher before enabling it.
  6. Exercise runtime death, provider outage, budget exhaustion, artifact loss and independent-review availability.

Completion evidence: identical local/remote receipt and transition fixtures; no cross-principal workspace reuse; replayed requests do not blindly repeat known or ambiguous effects; credentials expire and egress is constrained; remote kill switch and reconcile work. “Exactly once” is not a cloud-runtime guarantee.

Rollback: disable remote admission and reconcile outstanding remote work; local P2/P3 product stays usable. State after: a real hybrid execution fabric under one orchestrator. Example: two independent test slices run on customer runners and their evidence returns to one local integration owner.

11. P5 — Shared intelligence across projects

Goal: deliver one coherent outcome across multiple scoped Project Agents. Prerequisites: P4 release, P3 grants and per-project validators. No C stage required. Estimate: 6–10 engineer-weeks.

Capabilities: multi-repository work graphs, explicit fact grants, capability packs, ordered integration and evidence views. Single operator first; organizations/RBAC require a separate real-user demand and isolation design.

  1. Bind multiple Agents and grant only needed fact kinds across namespaces.
  2. Pin each repository base and define contract/ownership checks for the combined Spec.
  3. Compile a dependency graph and integration order; run independent work in parallel while preserving one canonical outcome.
  4. Evaluate optional Corbell architecture context/advisory findings with P5 fixtures and existing bench; C0 is not an entry condition.
  5. Present partial failures and all required evidence before any separately authorized draft publication. Do not imply atomic multi-repo Git publication.

Completion evidence: one real two-Agent outcome; cross-namespace denial, revision drift, migration/recovery and approval replay tests; staged changes remain reviewable on failure; any enabled publisher has per-effect reconciliation.

Rollback: revoke grants and new multi-project admission; retain linked single-project candidates and return to P4. State after: one shared intelligence can coordinate several projects. Example: an API pagination change and its UI consumer are verified together; Aether or Nemesis could use this, but neither is required.

12. P6 — Durable Goals that propose the next move

Goal: hold an objective over time and respond to new evidence with bounded proposals. Prerequisites: P5 release, runnable criteria and an evidence source. Estimate: 5–8 engineer-weeks plus a 30-day pilot.

Capabilities: human-confirmed Goal, evidence cursor, deterministic criterion evaluation, proposal dedupe, hard budgets and honest terminal states.

  1. Define Goal scope, runnable success criteria, call/money/time/blast-radius limits and terminal reasons; reject prose-only success.
  2. Subscribe to evidence revisions. Scheduled polling may discover new evidence, but unchanged fingerprints do not trigger model work.
  3. Evaluate cheap deterministic criteria first; generate at most one proposal per failing criterion/evidence pair.
  4. Require human review and a new confirmed Spec before a Job exists. Goals cannot create Goals or bypass effect authority.
  5. Persist cursors and budgets; test restart, exhaustion, changed criteria and explicit retirement.

Completion evidence: 30-day proposal audit links every proposal to new evidence and a failing criterion; duplicate notifications deduplicate; zero calls after budget exhaustion; no unauthorized Jobs or child Goals.

Rollback: freeze Goal evaluation/proposal generation and preserve inert history. State after: Legion remembers objectives and asks for the next authorized step. Example: a new CI receipt shows API drift; Legion proposes a repair once and waits for confirmation.

13. P7 — Evidence-gated policy improvement

Goal: improve context, routing, guidance and validation choices with measured outcomes. Prerequisites: P6 release and enough disjoint data for the declared experiment. Estimate: 8–14 engineer-weeks plus observation.

Capabilities: common promotion record/controller, held-out comparison, shadow/canary, authorized promotion, later-outcome monitoring and automatic reversion. This phase does not train models.

  1. Separate task execution status from human acceptance, defect/rework and later outcome labels.
  2. Implement legion.promotion-record.v1 with baseline/candidate/split digests, thresholds, vetoes, approver, expiry and rollback.
  3. Extend current context-tuning and report-only routing advice through one controller; freeze the experiment plan before reading results.
  4. Compare on project/time-separated held-out cases; shadow then canary only meaningful non-regressing candidates.
  5. Observe subsequent outcomes, retire bad guidance and auto-revert regressions. Keep source changes in the existing reviewed proposal flow.

Completion evidence: each controller accepts and refuses a candidate for reproducible reasons; safety/privacy/authority or false-success regression vetoes promotion; no single-episode law; old clients cannot reactivate retired policy. P7 owns the controller that C2 later extends, so there is no P7 ↔ C2 cycle.

Rollback: all controllers return to report-only and the prior pinned static policy. State after: Legion measurably improves selection without claiming better model weights. Example: a cached test fixture reduces accepted-task latency while the full applicable release gate stays green.

14. P8 — A mature shared verified platform

Goal: sustain reliable shared intelligence across authorized projects, tools and capacities. Prerequisites: P7 and longitudinal real-work evidence. Timeline: ongoing maturity; no C stage is required.

Capabilities: coherent world context, scoped Agent composition, durable objectives, proven effects and measured policy improvement, with operational ownership.

  1. Run representative cross-project workloads over sustained use and track acceptance, escaped defects, authority denials, cost and recovery.
  2. Close availability/retention/backup gaps; rehearse global freeze and disaster recovery.
  3. Prove that a prior verified outcome improves a later related task; retain attribution and disclose uncertainty.
  4. Audit capability claims against current versions and tests; reduce scope or freeze repeated failures under convergence.
  5. Publish operational ceilings and unsupported domains. Domain expansion requires its own Abilities and validators.

Completion evidence: zero unauthorized effects and false-success receipts in declared suites/pilot, successful recovery drills, sourced active knowledge, measured later-outcome improvement and independently usable P0–P8 delivery. Finite tests do not prove universal safety.

Rollback: global freeze stops new Goal proposals, policy canaries and remote claims; return to P5 human-directed delivery after draining/reconciling in-flight work. State after: a valuable platform even if every cognitive research bet stops. Example: Legion relates recurring release failures to a cross-project contract, proposes a bounded repair and proves improvement in later releases. Phase 9 earns any additional native-cognition claim.

15. MVP scope and the complete user journey

Planned contract The MVP is one personal, customer-hostable Cloud Hub, one Postgres database and one active outbound local Worker. A user may enroll two devices for continuity, but only one device is enabled for cloud-coordinated execution at a time. Switching the active device requires draining or reconciling outstanding work and explicit local enrollment/selection; existing Jobs never migrate silently. Every new Job selects its exact binding in the confirmed envelope. Multi-capacity execution arrives in P4. The Hub has no model/provider credentials, coding runtime, source checkout, cloud apply endpoint or publication endpoint.

  1. Bind locally: the CLI validates the repository and Agent, shows the proposed cloud-safe metadata and enrolls the binding. Paths and remote URLs stay on the device.
  2. Start anywhere: the user selects the logical repository/Agent and types a product message. Cloud stores this intentionally supplied message. It does not run a model to answer it.
  3. Clarify locally: a separate ClarificationRequest is queued to a selected binding. The Worker reads authorized local context in read-only mode, checks required fields, then uses an approved model if needed. It returns structured questions or a proposed Spec, never raw provider chat.
  4. Confirm exactly: a preview shows outcome, acceptance checks, constraints, exclusions, base commit, Agent/policy/profile, context snapshot, selected Worker and budget. Human confirmation binds these digests and an expiry. A confirmation is not permission to apply the future patch.
  5. Create and execute a Job: one idempotent submit consumes that confirmation. The Worker verifies all pins, acquires a fenced execution authorization, runs the existing lifecycle in isolation, validates and obtains eligible independent review.
  6. Receive proof: the cloud result names the Spec version, checks, review status, cost/usage assurance and a safe summary. Code-changing completion is review_ready. The detailed diff and evidence are inspected locally.
  7. Continue later: answers, changed strategy or new constraints create a new Spec version. Approved Ledger knowledge may help the next task; it cannot retroactively change what an earlier Job meant.

Changing the strategy or specification mid-run

A new message is an immutable input event. The user explicitly chooses whether it is a note for later or a material change to the current request. A material change appends a supersession event, requests cancellation of the old Job, and creates a new draft/clarification request. Old inputs, attempts, review and results remain linked to the old Spec. The new Spec must show the change and receive fresh exact-digest confirmation, even if the change sounds small.

While the prior Attempt is unresolved, no replacement code-changing Job starts for that session/repository. After cancellation/reconciliation settles, submit a new linked Job using a fresh confirmation. If the old Job completed first, keep its immutable result, mark it superseded in the session view and ask whether any local candidate is to be reused as a new base. Never label old evidence as validation of the new Spec. A late clarification response for an older message revision is historical only; it cannot overwrite the current draft pointer.

Out of scope: organizations/billing, multi-repo Jobs, federated graph ingestion, cloud coding/serving, remote shell, arbitrary URL fetching, automatic placement, cloud apply/commit/PR/merge/deploy, online training, Redis/Kafka/general artifact storage and a second orchestration or learning engine. A small independently durable safety journal alongside managed backup storage is required for safe restore; it carries control metadata only, not source or model artifacts.

17. MVP data model and storage

Logical identity: the Hub allocates a random opaque repository UUID. A local enrollment maps it to a verified path/remote identity privately. A second device explicitly joins that logical repository after local identity checks and user confirmation. Remote URL hashes, matching names or local learning IDs do not grant access or automatically merge repositories. Session portability: a session pins logical repository_id and Agent identity, not a device binding. Every Spec pins an Agent version and immutable base. Each clarification request and Job selects a currently authorized binding for that same owner/repository. A Job never silently changes device; a new binding selection requires a fresh execution-envelope confirmation and, after submission, a new linked Job.

Local storage and ordering

One Worker process: take the existing local file lock before starting the daemon, then register a unique process-instance ID against the enabled device and admission generation. Server instance-lease acquisition is CAS; all claims/heartbeats/starts carry that instance ID and instance fence as well as the Attempt fence. A second daemon cannot claim under the first daemon’s lease. An expired instance is not automatically replaced while any Attempt or hazard is unresolved. Recovery first proves the prior local process is stopped/contained, then advances the instance fence; it never transfers uncertain execution to another daemon.

Reuse resolved Core state, private session logs, run artifacts and locks (E4–E5). Add a private cloud-client SQLite database, 0700 directory / 0600 file, WAL, synchronous=FULL, foreign keys and bounded busy timeout. It stores binding-to-path mappings, claimed payload/fence/token references, start intents, stage/effect journal, terminal digests, outbox, cached safe objects and Ledger cursors. It does not replace all Core state.

Lease/refresh secrets are encrypted using an OS-secret-store key, not a key beside SQLite. Provider secrets stay in their existing local credential store. A corrupt database is quarantined; cloud admission stops pending evidence reconciliation. Never discard an uncertain claim and start it again. Local filesystem evidence is private, not tamper-proof against the machine owner.

Storage limit: MVP cloud results are typed metadata and small safe summaries, initially at most 256 KiB per terminal envelope and 16 KiB per progress event. No source/diff/log artifact upload route exists. Larger detailed artifacts stay local; a future general artifact store needs a measured need and a new data policy. The separate safety journal described in §20 holds only recovery control records. This replaces the ambiguous v3.1 “5 MiB artifact” allowance.

Canonical digest contract

Validate semantic objects before hashing. For v1, use a deliberately restricted JSON domain: NFC strings, booleans, null, arrays, objects with ASCII schema keys, and integers within the interoperable safe range; fractional costs use fixed-unit integers or defined decimal strings. Reject duplicate keys, NaN, infinity, ambiguous timestamps and unsupported numbers. Normalize timestamps to RFC 3339 UTC. Serialize this restricted domain with RFC 8785-compatible canonical ordering/escaping; cross-language golden fixtures are mandatory. Do not call ordinary “sorted JSON” universal JCS.

Digest is sha256:<lowercase hex>. Each schema publishes covered fields; exclude its digest and transient transport fields. Manifest digests cover the parsed semantic object and pinned instruction/plugin references; formatting alone is not semantic change. Raw artifacts use exact-byte hashes with a distinct media/type marker. A digest detects mismatching bytes, not who authored them. MVP trust is authenticated requests, authorization, local checks and retained receipts; no new cryptographic signature system is asserted.

Spec and clarification lifecycle

Current-intent guard: confirmation binds session_id, current_spec_id, execution_generation, spec_digest, envelope_digest. Supersession, selecting a materially different draft, or changing semantic execution pins locks the session row, advances its execution generation, appends confirmation-invalidation events and requests cancellation of any old nonterminal Job in the same transaction. A note explicitly marked for later does not advance the execution generation. POST /jobs locks the admission/session rows and rechecks the current Spec, generation, digests, unexpired/uninvalidated confirmation and absence of unresolved hazards before consuming confirmation. A confirmation invalidated between preview and submit yields conflict and no Job. First-start authorization repeats the current-generation check so a queued stale Job cannot race a new intent.

Clarification egress guard: model selection alone does not authorize disclosure of repository data. Before submitting a clarification request, show the selected provider, permitted data categories, purpose and expiry from a pinned human-approved egress grant. Enrollment may establish a reusable narrow grant; absent or wider authority requires a scoped approval before the request is queued. The request pins the grant digest. Worker preflight and every new provider invocation check the grant, local binding, revocation, expiry and actual selected data against its limits. Missing, expired or mismatched authority blocks provider calls; deterministic local checks may still return bounded questions. Neither a model nor the Cloud Hub may mint or widen the grant. This authority precedes the first Spec and is distinct from later confirmation of code-changing work.

A request explicitly marked deterministic_only needs no provider-egress grant and cannot invoke a provider; its deadline and local budget still apply. All model-enabled clarification requests require the grant before queueing. Grants constrain provider-bound data, not permission to synchronize the same data to the Hub.

Spec versions are immutable drafts/proposals; “confirmed,” “current” and “superseded” are derived from separate confirmation/session events. Each user answer creates a new draft/request, not an in-place edit of confirmed content. The local clarification result resolves the base SHA before confirmation; execution never resolves a moving branch after approval. A request for an old message revision may finish but cannot advance the current session pointer.

Session display state is a projection of these records, not another execution state machine: drafting, needs_input, ready_for_confirmation, queued, executing, cancellation_pending, reconciling, review_ready, blocked or closed. Supersession uses expected session revision to append the change, advance the draft pointer and request cancellation atomically. Historical clarification/Job results remain visible under their own versions.

Event batches acknowledge the highest contiguous accepted sequence and identify conflicts. Identical event ID + digest is a no-op; changed bytes conflict. Publish terminal success only after all declared event/receipt dependencies are present or explicitly classified optional by the pinned schema.

19. Worker execution, leasing and recovery

  1. Recover first: on startup inspect durable claims, local supervisor identity, stage journal and outbox. Resolve these before claiming more work. Never infer “not running” from a missing PID alone.
  2. Claim: outbound long poll carries device/runtime/capability identity. In a short transaction, Postgres first locks the deployment’s execution-admission row and verifies active device/generation and the appropriate free slot, then selects an eligible work owner with FOR UPDATE SKIP LOCKED, validates binding/version/deadline and inserts an Attempt with a new monotonic fence. An unresolved Attempt excludes further claims for that work owner and still occupies its admission slot. Release the transaction before returning to long polling.
  3. Persist then acknowledge: commit payload digest, owner pins, lease secret and Attempt/fence to local SQLite before sending ack. If ack response is lost, query/reconcile that Attempt; do not create another.
  4. Preflight without task effects: verify device/binding, local repository identity, exact commit, authoritative Agent, plugin/profile/policy/runtime and knowledge snapshot. Read-only checks may inspect installed files/config; they must not invoke a task model, mutate a worktree or fetch arbitrary remote content. Temporary provider/capacity unavailability releases before start with durable backoff; drift/denial blocks.
  5. Authorize the start: write a local start-intent, then POST start. The server atomically checks cancellation/expiry and records start_authorized_at, Attempt running and owner running. Persist the response before launch. Lost response is reconciled; a start marker means “may have executed,” even if launch never happened.
  6. Execute locally: create the dedicated worktree at the already confirmed SHA. Compile bounded Context Packs, pin their digests, and run the entire allowed lifecycle under the current process supervisor and supported sandbox. Clarification uses a read-only profile; code Jobs use the confirmed effect scope.
  7. Journal bounded actions: before each model/tool stage record input digest, intended action and recovery class. Afterward record outputs/exit/evidence. The supervisor/Worker heartbeat loop is independent of provider child progress.
  8. Validate and review: choose affected checks only under the pinned validation policy, run mandatory acceptance gates and review the exact integrated candidate with actual author provenance. A model text saying “passed” is insufficient.
  9. Commit before upload: fsync detailed local evidence, then atomically commit terminal result digest and safe outbox event in SQLite. Upload only allowlisted receipts/summary; Hub verifies manifest coverage and terminalizes owner + Attempt in one transaction.
  10. Acknowledge and retain: only after the committed response may the outbox entry be marked delivered. Keep local candidate/evidence according to retention. A later local apply is separately digest-guarded.

Lease and cancellation rules

Initial tuning 25-second long poll, 90-second lease, 20-second heartbeat; validate these under pause/load/crash tests before execution rollout. Database time decides expiry. The Worker uses monotonic time and a conservative renewal deadline locally; it cannot extend a lease by changing its clock.

On missed renewal/lease loss, stop admitting new stages and model calls. The already-started bounded isolated action may finish within its local timeout while the Worker preserves evidence; otherwise the supervisor stops it. No Hub success is claimed until reconciliation. This is a deliberate safety limit for cloud Jobs. Standalone local Legion has no Hub lease and remains independent of a Hub outage. Remote-model stages in either mode still require provider connectivity.

Cancellation is a durable request returned on heartbeat/poll; the Hub sends no local process signal. Worker revalidates process identity and invokes the existing supervisor. macOS needs inherited sandbox fingerprint/canary coverage; Linux needs the supported pidfd/process-identity path. Unsupported inspection fails closed. Cancellation means stop future work and settle effects, not erase already-produced local code or undo a provider charge.

Resume requires the same device’s matching payload and journal, fresh authentication, current binding/authority, and a new lease epoch/fence. A stale holder cannot commit progress/results after renewal elsewhere. Fencing protects Hub transitions; it cannot stop a disconnected rogue process or guarantee an external provider obeys the fence. Device trust, local supervision, admission limits and reconciliation cover that boundary.

Never auto-reassign an Attempt after start authorization. Human abandonment records blocked:attempt_abandoned and preserves uncertainty. Before a replacement Job is authorized, the operator must establish that the prior execution is stopped/contained and reconcile any relevant external effect; missing evidence is not proof of no effect. MVP contains code changes in an isolated local worktree and forbids external publication, but provider calls may still have consumed quota.

Retries, backpressure and commands

Retry safe requests on network/408/425/429/5xx with full-jitter exponential backoff, bounded Retry-After, attempt/deadline caps and persisted not_before. Start near one second, cap near five minutes; tuning is measured. Acknowledged model/tool calls are not automatically replayable. Authentication, policy/schema/digest conflict, tombstones and ambiguous effects require repair or reconciliation, not a retry loop.

Planned CLI: legion-worker start|once|status|doctor|install-service|uninstall-service; legion-cloud login|bind|agent|sync|status; scoped Ledger propose/promote/retire; human recovery inspect/abandon. These commands deepen existing modules; they are not currently installed capabilities established by this document.

Authentication, isolation and key ownership

Browser login uses an established OIDC authorization-code/PKCE flow with state/nonce and Secure, HttpOnly, SameSite cookies; mutations require origin/CSRF checks. Device enrollment requires interactive human approval, short access tokens and rotated hashed refresh tokens. Scope devices to owner and bindings; recheck revocation on claim, start, heartbeat, result and resume. Workers cannot confirm Specs, register validators or approve human-authority knowledge.

TLS, encrypted database/backups and envelope encryption for product content are required before real data. The deployment operator owns the KMS/root key: the customer in customer-hosted deployments, the service operator in any later managed offering. Data keys carry versioned key IDs and authenticated metadata binding owner/table/record; rotation rewraps keys with an audited migration. The application can decrypt for authorized flows, so the design makes no E2EE or protection-from-deployment-admin claim. KMS outage or authentication failure fails closed; never fall back to plaintext.

Separate Hub credential environment from provider subprocesses, restrict filesystem/egress by profile, use parameterized SQL and argument arrays, escape UI text and enforce CSP. Pin Worker/runtime/plugin dependencies and artifact digests. Cryptographic release signing may be adopted only through a separately specified key/distribution/rotation process; it is not assumed as a substitute for authenticated requests or a present feature.

Retention, deletion, audit and backup policy

Pilot defaults to approve before real data Product messages/Specs/terminal metadata: 30 days after session closure; idle active sessions require an explicit renewal or expire after 90 days. Local detailed logs/candidates: separately configurable, initially 30 days with visible cleanup/export. Content-free audit: 180 days. Knowledge: kind-specific expiry, with review at least every 90 days; no unbounded active fact without an owner. Idempotency response cache: at least 7 days, while confirmation-consumption records and minimal tombstones survive the replay/backup horizon.

Deletion immediately tombstones the target, denies new reads/admission/context use, requests cancellation and rejects late uploads. If an Attempt is unresolved, retain only the minimum encrypted recovery data under a documented deletion-pending state; operator escalation must resolve or quarantine it within a defined limit (pilot target 7 days). After settlement, purge message/Spec/result ciphertext and derived caches (pilot target 24 hours), retaining minimal content-free audit/deduplication identifiers. A valid old digest is not permission to resurrect deleted content.

Backups initially expire within 30 days. Restore into quarantine and apply the independent safety journal below before serving any product content or admitting execution. Advertise deletion completion separately for live storage, device acknowledgement and backup expiry. A disconnected device, exported file or external provider cannot be remotely erased on demand; show pending local cleanup and enforce tombstones on reconnect. Never claim instantaneous global deletion or removal of information from already-trained weights.

Backup-independent safety journal and restore admission

Required storage boundary: deletion tombstones, device/grant/validator revocations, confirmation invalidation/consumption, execution-start intents and unresolved-hazard records must survive restoring an older Postgres backup. Retain these content-free records in an operator-controlled, encrypted, versioned append-only journal outside that database’s backup/restore domain. A managed object-storage journal with conditional append/head updates is an implementation option; it is backup infrastructure, not an artifact warehouse or second Job engine. Postgres remains the live coordination ledger.

Write protocol: authenticate and validate the control request, allocate its idempotent event ID, then durably append a deny-first control intent before committing the matching Postgres transition. An append succeeds only when its event bytes and monotonic high-water record are durably readable outside the restored database. Bind sequence, previous digest, deployment identity, event kind, opaque target IDs, policy/Spec digests and actor reference; store no content, path or credential. Acknowledge the control mutation only after both journal and database receipts exist. Start authorization likewise requires the journal receipt before permitting a Worker launch. Journal outage fails closed for these operations; bounded timeouts and an operator-visible pending state prevent a hidden retry loop. An intent whose database commit failed remains conservatively denying until an idempotent reconciler applies or an authorized recovery disposition resolves it; it never grants permission during replay.

Record verified terminal-settlement and containment receipt references in the same journal before acknowledging their safety-state transition. Replay may add denials or uncertain-work records; a favorable settlement is not permission to execute and clears a hazard only after recovery verifies its evidence and current authority. The journal never issues leases or dispatches tasks. Its monotonic append/high-water adapter and failure behavior are a required S5 contract, not an assumed property of any arbitrary object bucket.

Recovery point: acknowledged safety-control events have a required loss budget of zero within the declared backup-restore fault model, separately from the 24-hour product-content RPO. Keep journal records and a verified compacted denial/hazard snapshot beyond the oldest restorable backup and token/replay horizon; never prune them merely because their database rows were restored. Journal high-water and retention controls must not roll back with Postgres. Missing or unverifiable journal coverage blocks restore rather than assuming no deletion/revocation occurred. This does not promise survival of an operator destroying every independently retained copy.

Restore protocol: freeze claims and content reads; create a new random deployment restore epoch in the independent control store; invalidate all prior Worker/Attempt lease tokens and refresh sessions. Replay journal records through the latest verified high-water mark, reapply deletions/revocations and quarantine any start intent without sufficient settlement evidence. Reauthenticated Workers report their retained claim/start/result journals through a restricted recovery channel; original digests and epochs remain historical evidence, never fresh execution authority. Reconcile or explicitly contain every uncertain execution before enabling new work. Jobs absent from the restored backup are not automatically reconstructed as executable Jobs; recover evidence or require fresh confirmed work after containment. All new admission/lease tokens bind the new epoch, preventing restored counters from making an old token valid again. Only after these checks may the operator reopen product reads and execution; unreachable devices or journal gaps remain visible blockers.

Audit accepted and rejected enrollments, confirmations, claims, policy mismatches, promotion, cancellation, reconciliation, revocation and deletion using IDs/reasons only. Audit is append-only under application permissions but not magically immutable against a database administrator. Retained evidence is immutable while retained; required content deletion replaces it with a tombstone and may make later reproduction impossible. Report that loss of evidence honestly.

28. C0–C6: goals, work and exit evidence

C0 — Evaluation and data constitution

Goal: measure cognitive quality before claiming improvement. Prerequisites: P0. Capabilities: versioned datasets, sealed holdouts, deterministic scorers, task IDs, rights/eligibility and claims records.

  1. Inventory software, retrieval, architecture, tool-selection, research and domain task classes.
  2. Define objective outcomes, known limits and baseline configurations; separate authoring data from held-out projects/time windows.
  3. Predeclare sample size/power, stopping rule, useful-effect threshold and safety vetoes; freeze holdout access.
  4. Run existing benchmark infrastructure and retain reproducible baseline reports, including failures and uncertainty.

Completion evidence: repeatable scorers, rights/split manifests, contamination checks and reports covering quality, clarification, review, latency and total cost. LLM judges may be advisory, never sole success gates. Rollback: remove additive experimental suites without affecting P gates. State after: research can be compared honestly. Example: a report shows whether a clarifier finds required missing fields better than a deterministic checklist.

C1 — Bounded dynamic cognitive topology

Goal: choose a useful reasoning structure for a task. Prerequisites: P1 + C0. Capabilities: typed temporary roles/edges, replayable compiler, policy/budget clamps and static rollback; external models still provide reasoning.

  1. Define legion.cognitive-topology.v1: Spec/Agent/context/policy/compiler digests, nodes, typed edges, aggregation, Abilities, Provider/Capacity constraints, validators and stop budgets.
  2. Implement a pure compiler into existing plan/slices. It rejects unknown roles, cycles not covered by bounded iteration, authority widening and missing validators; it cannot dispatch or transition Jobs.
  3. Compare fixed shapes: single bounded role, scout→implement, plan→implement→review, independent fan-out→integrate→review, and bounded critic/repair.
  4. Shadow selection, then canary only an explicitly approved policy. Retain the static baseline for every task class.

Completion evidence: same pinned topology/compiler produces same plan digest; adversarial authority/budget fixtures fail; useful paired lift or efficiency at non-inferior quality; no false-success regression. At least 30 paired cases is a starting floor, not automatic statistical sufficiency. Rollback: disable topology selection and use the authorized static policy for new Jobs; mismatches block unless that fallback is already permitted. State after: reasoning structure is measurable and replaceable. Example: a flaky-test repair uses one bounded critic pass while independent API tasks use fan-out, both with the same proof gates.

C2 — Governed data and promotion factory

Goal: create a legitimate path from authorized evidence to a learned artifact. Prerequisites: P7 + C0. Capabilities: dataset/component manifests, lineage, quarantines, sealed evaluation, shadow/canary and rollback using P7’s controller.

  1. Define dataset rights/purpose/authority, eligible fields, source/split digests, retention and withdrawal obligations. Ordinary product content remains excluded.
  2. Register code/recipe/base-model/data/artifact lineage and permitted roles; digest-pin artifacts and dependencies.
  3. Evaluate against sealed holdouts with predeclared thresholds and safety vetoes; require human promotion authority and a previous green version.

Completion evidence: missing rights, contamination, train/eval overlap, missing rollback and known author/reviewer derivation fail; a forced regression reverts; connected clients reject quarantined versions and disconnected clients stop new learned-artifact use at a bounded locally enforced policy expiry. 30. Learning rights, withdrawal and claims limits

Data authority: deployment ownership is insufficient training permission. Every dataset import names rights holder, license/authority, purpose, field eligibility, source revisions, retention and withdrawal obligations. Ordinary tenant code, prompts, diffs, messages and provider logs remain excluded unless separately imported with sufficient rights and explicit governed authority. No cross-tenant aggregation by default. Authorized provider egress for a task is not consent to Legion training.

Withdrawal: stop new ingestion, invalidate affected dataset versions, traverse lineage and quarantine downstream artifacts for new deployment. Connected clients receive revocation; disconnected clients stop admission at a predeclared locally enforced authorization expiry and on reconnect. This depends on a cooperative trusted runtime and clock/expiry handling, not a newly invented signing protocol. In-flight work stops at safe boundaries, retains evidence and reconciles.

Deleting source rows does not remove their influence from weights, copies, previously generated outputs or external provider systems. Do not promise mathematical unlearning, instant remote erasure or global withdrawal from uncontrollable exports. Affected artifacts require rights-compliant retraining/re-evaluation, demonstrated remediation where valid, or retirement; disclose technical and contractual limits. If withdrawal cannot be honored as required, do not ingest that dataset in the first place.

Governance: decision components enter a versioned component/policy registry; reasoning models enter the Provider/model-policy registry. Digest pins and authenticated promotion records identify artifacts; ownership alone grants no authority. Future cryptographic distribution signing requires a separate threat model and key lifecycle. Learned components never solely validate correctness, grant trust, approve actions or gate high-consequence effects.

Claims: the planned claims registry maps each public statement to a named test, evidence digest, covered source/model/policy versions, owner and expiry. CI should reject unsupported/stale claims once this gate is implemented. Avoid claims of AGI, consciousness, zero hallucination, universal competence, guaranteed alpha or global competitor superiority. A native model must earn named behaviors just like an external Provider.

High-consequence domains: research, forecasts, backtests and strategy proposals remain advisory. A live financial, spending, deployment or irreversible-migration effect belongs to a separately owned typed Ability outside Core with exact action/limits/expiry approval, deterministic fresh-state checks, effect-specific idempotency, emergency stop and outcome reconciliation. For trading, include account/instrument/side/order type/quantity or notional/price or slippage/risk limits. A fill cannot be “rolled back”; containment or compensating action is separate authority. Models/Goals have no standing brokerage credentials or permission to change risk policy.
