Legion Core

The domain-neutral harness kernel and local runtime. It owns versioned contracts and pure reducers for outcome intents, Specs, Durable Goals, work graphs, Project Agents, Abilities, Providers, Capacities, evidence, knowledge claims and policy. It MUST NOT import Cloud infrastructure.

Legion Cloud Hub

An optional modular application that supplies identity, encrypted sessions/specs, durable jobs, Project Agent registry, trusted memory, Knowledge Ledger, policy and audit through published Core contracts. It coordinates work; it is not the coding container.

Project Agent

A repository-bound, versioned manifest plus scoped memory, abilities, context and proof policy. Nemesis and Webapp become different Project Agents over the same Legion intelligence. Planner, implementer and reviewer are temporary role instances inside a Job, not separate orchestrators or workers.

Knowledge Fabric

One logical, authorized world model over source systems, typed trusted memory and attributed graph claims. It is federated: Git, issues, docs and telemetry remain authoritative; Legion retrieves a bounded task subgraph rather than copying or prompting “everything.”

Ability

A typed, permissioned operation supplied by a skill, domain plugin, MCP/ACP adapter or small executable. Every side-effecting ability declares its input/output, authority, validator, timeout and recovery behavior.

Provider

Which approved adapter performs a work unit and, for model work, which effective model and effort it attests: Claude Code, Codex, another harness, or a future native adapter.

Capacity

Where work runs: a laptop, build box, customer runner, CI lane, or cloud sandbox. Each has its own identity, credentials owner, trust class, capabilities, cost and concurrency.

Context source adapter

A read-only adapter for bounded, attributed facts such as code graphs, decisions, issues, incidents, docs or runtime telemetry. Its text is never trusted instruction; “Provider” remains reserved for execution.

Integration capacity

Exactly one Capacity hosts composition. Sol authors application and conflict-resolution edits under Opus integration decisions; Opus then independently reviews the integrated candidate. Fan-out may distribute, but composition never does.

Outbound worker

A Capacity-side daemon that claims, durably records, verifies and runs Jobs. It is not a Project Agent, a model role or an orchestrator; it may change execution state only through fenced Core transitions.

Outcome intent and Durable Goal

An outcome intent is the bounded request captured by a Spec in Phases 0–5. A Durable Goal is the Phase 6 evidence-watching entity; it can emit only a Proposal, and only a human-confirmed Spec can create a Job.

Dynamic Cognitive Runtime

Proposes a typed, bounded role topology for one immutable Spec. A pure compiler validates and clamps it to Agent/Ability/model/effect/budget policy, then emits the existing plan.json/slices.jsonl inputs; only the existing orchestrator may commit the canonical work graph. The runtime cannot dispatch work, invoke an Ability or transition a Job, so it is not a second workflow engine or authority path.

Profile and Domain Mind

A Profile is a versioned Project Agent-like manifest plus scoped namespace, promoted policy/component set and required validators. A Domain Mind combines a Profile with domain data, Abilities, evaluators and Providers; neither is a process, authority or personality layer.

Native Cognitive Engine

A separate legion-cognition program owns governed datasets, training recipes and signed learned artifacts. Decision components enter Legion through the component/policy registry; native reasoning models enter through the Provider/model-policy registry. Both remain behind Core contracts, while weights and domain datasets never live in legion-core.

Evaluation and claims plane

Sealed holdouts, dataset/lineage manifests, promotion records and claims.toml decide what may ship and what may be said publicly. Safety, privacy, authority or false-success regression vetoes promotion regardless of quality gains.

Enforceable dependency direction

legion-contracts → Core kernel and local adapters → optional repo/domain abilities. Cloud and Worker Runtime adapters depend on the same contracts; Core never depends back on them. “One logical orchestrator” does not require one process: Cloud Hub and Workers apply the same single-owner reducers, and a nested legion-run may coordinate role instances but cannot create a second canonical Job truth. Project-specific manifests and domain plugins live with their project or plugin, never in legion-core.

6. Phase 0 — Lock the kernel

Clear goal

Stabilize current contracts and explicitly migrate the initial model policy while splitting provider from capacity.

Why

Cloud and multi-machine work cannot safely attach to informal run-state files or an executor field that means both “what” and “where.” The requested production Opus/Sol xhigh policy is a real behavior migration and must be canaried, not hidden inside a “no behavior change” refactor.

Estimated effort

Assumption 2–4 engineer-weeks, including compatibility fixtures and baseline measurement.

Features and ordered steps
  1. Update and pin the implementation baseline; record the exact Legion version on every attempt and receipt.
  2. Promote the shapes needed before cloud to JSON Schema: outcome intent, work session, Spec, Project Agent, Ability, Provider, Capacity, Job, Attempt, provider invocation, Receipt, Approval, knowledge assertion/validator, grant, Context Pack and canonical digest. Add effect_class to Ability; high_consequence requires deterministic validators, human approval and recovery. Reserve Durable Goal/cognitive contracts for later gates.
  3. Add capacities.toml with one capacity: local. Keep executor as a compatibility alias for provider.
  4. Add provider_id, capacity_id, requested/effective model effort and fallback state to invocation spans/receipts. An Attempt pins its Capacity and provider-set digest; its provider-invocation manifest records each work unit separately because one Job may use both Opus and Sol.
  5. Add graph-ready scope, entity, provenance, sensitivity and source-revision fields to memory and context contracts without building a graph database.
  6. After contract shadowing is green, migrate to the Opus 5 / Sol xhigh production policy behind a versioned profile and canary flag. Attest effective model/effort and disable unapproved fallback.
  7. Make legion.model-policy.v1 enforceable for delegated and primary work: define the canonical effort ladder low|medium|high|xhigh|max, require an exact per-harness mapping and effective attestation, fail closed when a requested level is unrepresentable, invert Claude fallback to opt-in, and remove/disable policy-bound routes to unapproved models. Aliasing max to xhigh is not an exact mapping.
  8. Preserve review independence through authoring provenance: Sol authors implementation/composition; Opus reviews. Define the future independence field over runtime author, underlying attested model and component-training lineage so a learned reviewer cannot train on the author’s outputs and call itself independent.
  9. Migrate legion-optimize.py and every remaining catalog consumer to the canonical legion-route.py reader; delete direct model-catalog parsing rather than maintaining two readers.
  10. Classify every stored field on two independent axes: sync policy (local-private|cloud-eligible|forbidden) and training policy (training_eligible, default deny, with rights/provenance). Product data is never inferred eligible from use; proprietary domain data enters only through an explicit governed dataset import.
  11. Add span retention before any telemetry projection can leave the machine.
  12. Rewrite public “no Legion server/cloud” guarantees to the accurate invariant: cloud is optional and customer-hostable; local-only remains complete.
  13. Add claims.toml and legion-doctor --only claims: every public claim names its test, evidence artifact, last green run and expiry. CI fails stale, unsupported or untested claims.
  14. Capture golden local runs, latency/cost/token baselines, privacy fixtures, and zero-false-success baselines.
Non-goals, optimizations, gates

Non-goals: no cloud, network, new planner, UI rewrite, queue or worker fleet. Apart from the separately gated model-policy migration, no execution behavior changes.

Optimizations: validate schemas at boundaries, not on every span append; reuse the single model-catalog reader and current atomic state writers; translate old artifacts only at ingress/egress.

Definition of done: current commands and full suites pass; new schemas have positive/negative/boundary fixtures; golden runs replay compatibly; unknown Provider/model/effort fails before invocation; policy-bound self work refuses unattested effort; fallback is explicit; no live policy-bound route reaches an unapproved model; receipts prove requested/effective model effort and fallback state; high_consequence and training-default-deny fixtures fail closed; every public claim is green in the claims doctor. Core imports neither Cloud nor Track B training/serving code.

Rollback: additive contracts begin in shadow mode. The model policy begins observe-only, then canaries by repository; one profile switch restores the prior static routing. No destructive data migration.

State after Phase 0

Legion is a pinned, contract-stable local execution foundation that knows both who performs work and where it runs.

Example: the same bug-fix delegation still returns the same patch and review evidence, now also bound to provider, capacity, Legion version, model policy and a schema-valid receipt.

7. Phase 1 — Local Project Agent Alpha

Clear goal

A user states a software outcome to a repository-specific Project Agent; Legion asks blocking questions, confirms a spec, performs the work locally, proves it, and returns a review-ready candidate from one command.

Why

Cloud should amplify a complete product. It must not be used to hide the absence of a first-party work session, spec ledger, planner, or resumable harness lifecycle.

Estimated effort

Assumption 5–8 engineer-weeks after Phase 0.

Features and ordered steps
  1. Add local legion-session and an append-only work-session journal. It stores outcome intent, Spec versions, decisions, stages, evidence digests, approvals and costs—not provider reasoning and not a Durable Goal runtime.
  2. Add legion-spec with immutable versions, blocking questions, explicit user confirmation and content digest.
  3. Add legion.project-agent.v1, a repo-owned manifest that references existing instructions, allowlisted domain plugins/skills, context sources, proof policy and allowed workflow profiles. Pin its digest to every run.
  4. Add deterministic required-field prechecks, then Opus 5 xhigh structured clarification for ambiguous work.
  5. Add a first-party planner that emits the existing plan.json and slices.jsonl contracts; no new workflow language.
  6. Use Sol xhigh for bounded implementation/test/debug/security/performance slices in existing worktrees.
  7. Use Opus xhigh for product/architecture/integration decisions and independent final review. Sol xhigh authors implementation, composition and conflict-resolution edits; candidate authoring provenance containing Opus fails the automated independent-review gate.
  8. Keep the integrated candidate in a dedicated worktree until exact-digest local approval. Do not touch the operator checkout.
  9. Make the lifecycle resumable from session events and periodic snapshots. Reuse convergence for no-progress detection.
  10. Build the entire safe projection/cache/outbox locally in shadow mode with no network transport.
Non-goals, optimizations, gates

Non-goals: no cloud, team accounts, remote agents, multi-repo job, auto PR/merge/deploy, hidden-reasoning store, unrestricted self-editing, or generic workflow engine.

Optimizations: deterministic search/schema/Git/test selection before model calls; repository context cached by immutable tree SHA; cheapest-failure-first validation; bounded context; unchanged checks skipped by source/evidence fingerprint; existing fan-out capped by measured capacity; reduce call count rather than reasoning quality.

Definition of done: representative feature, bug, refactor and test-hardening tasks complete from one command; ambiguous requests produce questions and no diff; process-kill/resume tests pass at every stage; candidate remains isolated; validation and independent review are mandatory; zero false success; self-learning finalization is attempted on all terminal paths.

Rollback: flags disable sessions, planner and resumability independently; explicit plan/slices mode remains available.

State after Phase 1

Legion is a durable local harness in which each repository can expose a real specialist without training or hosting a separate model.

Example: the Nemesis Project Agent loads Nemesis instructions and trading validation abilities, turns “add an RSI strategy” into a confirmed spec, isolated Sol implementation, deterministic backtest gates, independent Opus review and a review-ready patch.

8. Phase 2 — Hybrid Cloud MVP

Clear goal

Give one user a durable shared Legion across devices and repositories: encrypted sessions/specs, one Project Agent per bound repo, a trusted Knowledge Ledger and durable jobs executed through one outbound local worker—while local Legion remains fully useful offline.

Why

This delivers continuity and remote initiation without taking on cloud code execution, cloud provider credentials, or an untrusted worker fleet at the same time.

Estimated effort

Assumption 8–12 engineer-weeks after Phase 1. Detailed implementation plan begins in Section 15.

Features
  • One customer-hostable cloud application and one managed Postgres database.
  • User login, trusted devices, opaque repository bindings, cloud work sessions/messages, immutable spec versions, durable jobs/attempts/events, spec confirmation and audit. Cloud MVP has no patch-apply or publication approval.
  • Project Agent registry with one logical repo-owned legion.project-agent.v1 identity/version per logical Repository and agent name, shared by all authorized device bindings. Cloud stores only its safe projection/digest; each Worker verifies the authoritative manifest at the pinned commit.
  • Safe personal/repository memory plus a Knowledge Ledger of typed facts, decisions, preferences, validators and verified outcomes. Every record carries scope, source/revision, trust, freshness, sensitivity, supersession and tombstone state.
  • A bounded Project Context Projection always combines the confirmed Spec, active Project Agent and local repository facts; approved Ledger assertions are an additive source enabled only after their separate gates. The empty-Ledger snapshot is a legal, pinned first-class value.
  • Outbound-only legion-worker using local repositories, existing subscription credentials, approved profiles and current Legion workflows.
  • Long-poll claims, leases, heartbeats, cancellation requests, crash reconciliation, safe incremental progress and immutable terminal result.
  • Minimal UI for conversation, questions, spec confirmation, job start/cancel/status and review-ready result.
  • Cloud stores encrypted user conversation/spec bodies by explicit product choice; it never stores provider transcripts, terminal streams, local paths, repository source or provider credentials.
  • Launch hypothesis: continuity plus a repository that remembers its approved decisions is explicit MVP value. Cloud auth/binding starts only after the local Project Agent vertical slice is green; cloud Project Agent binding is required for sessions/Jobs; Knowledge Ledger context activates later, only after separate privacy, provenance and learning-lift gates pass.
Non-goals, optimizations, gates

Non-goals: no federated knowledge graph, graph/vector database, whole-repo ingestion, cloud coding worker, remote sandbox, arbitrary remote shell, inbound workstation access, auto PR/merge/deploy, organizations, billing, object store, Redis, Kafka, Step Functions, microservices, or automatic placement.

Optimizations: Postgres row leases; long polling; batched progress/Ledger events; ETag/revision pulls; SQLite WAL outbox; cache-first project context; manifest/context cache by commit and digest; no token streams; one Job per Worker by default; current bounded fan-out inside the Job. The basic cloud-to-local path never waits for active Ledger context.

Definition of done: a user starts a cloud session on another device, selects a bound Project Agent, answers questions, confirms a digest-bound spec, and an outbound local worker verifies the pinned manifest and executes current Legion. Cloud shows review_ready; two devices converge on approved Ledger state; conflicting/untrusted facts cannot silently enter context; restarts never cause a blind duplicate effect; privacy/model-policy/denial/deletion/rollback gates pass; ordinary local Legion works with network physically disabled.

Rollback: cloud sessions, Project Agents, Jobs, Knowledge Ledger/context and Worker execution flags are independent; disabling all returns Phase 1 while preserving local evidence and unsent outbox records.

State after Phase 2 — MVP

Legion is a usable local-first cloud intelligence: one durable identity and memory, multiple repo specialists, and one trusted outbound local worker.

Example: from a phone, the user asks the Nemesis Project Agent to add an RSI strategy; the workstation returns focused questions, receives confirmation, pins the repo and manifest, runs the approved Opus/Sol xhigh production policy locally, and the phone later shows review_ready while code, credentials and raw provider logs never leave the workstation.

No C-stage artifact may enter any P0–P8 critical path, definition of done or release gate. Track B may measure in parallel, but every Platform phase—including the Hybrid MVP—must remain independently completable and rollbackable.

9. Phase 3 — Federated Knowledge Fabric

Clear goal

Turn trusted ledger records and live source-backed context into one authorized, federated world model with bounded Project Agent views.

Why

A shared intelligence needs relationships among repositories, APIs, decisions, owners, incidents and evidence. It must preserve source authority and permissions rather than copying “everything” into an opaque memory database.

Estimated effort

Assumption 6–10 engineer-weeks for the ontology/contracts, project graph, two source adapters and retrieval evaluation.

Features, optimizations, gates
  • legion.knowledge-assertion.v1 for typed entities, relations and assertions, plus legion.grant.v1 for explicit expiring cross-namespace reads; absence is denial.
  • A deep Context Broker that plans a query, fetches allowed sources, resolves identities without hiding conflicts and returns a bounded, digestible task subgraph with an inclusion reason for every fact.
  • Local Git/rg/repo instructions and legion-code-intel remain the baseline. Graphify is evaluated as a removable read-only local code/docs graph adapter; it is not assumed or required.
  • Detailed source graph stays in a droppable local SQLite projection. Only allowlisted typed assertions/edges publish to a safe cloud Postgres projection. Project Agents see their repo subgraph plus explicitly granted facts; permission applies in the query.
  • Context-source text remains untrusted evidence. Independent sources fetch concurrently under time, byte, fact and token budgets; cache/invalidate by pinned source revision and query digest.

Non-goals: no source-system replacement, full-database copy, global ontology for every domain, writes back to source systems, automatic trust promotion, dedicated graph/vector database without measured need, or semantic retrieval without held-out evidence.

Optimizations: Postgres typed nodes/relations first; incremental indexing; deterministic graph traversal before semantic search; bounded task subgraphs; source-specific invalidation; content digests; concurrent independent fetches; no whole-graph prompt.

Definition of done: two source adapters satisfy one contract; Nemesis and Webapp receive permission-correct subgraphs; a cross-repo dependency traces to evidence; stale/conflicting/poisoned facts remain visible or excluded; deterministic projections rebuild to the same digest; source outage restores baseline behavior; Graphify or any external adapter ships only after predeclared held-out lift beyond Git/rg/legion-code-intel, zero unauthorized facts and supply-chain review.

Rollback: every context-source adapter defaults off and has its own kill switch. Disabling all source adapters restores Phase 2 context behavior without changing the Harness interface or persisted jobs.

State after Phase 3

Legion has an authorized world model: one logical graph, federated sources and bounded Project Agent views.

Example: Legion knows that a Nemesis strategy schema is consumed by the Webapp, cites the symbols, API contract, owner, ADR and prior incident behind that relationship, and coordinates both agents without exposing unrelated private context.

Canonical digest contract

legion.canonical-digest.v1 is shared by every local/cloud adapter. Structured input is first schema-validated, Unicode strings are normalized to NFC, timestamps are normalized to RFC 3339 UTC, unsupported numeric values are rejected, and the covered semantic fields are serialized as RFC 8785 JSON Canonicalization Scheme bytes. The digest is lowercase sha256:<hex> over those UTF-8 bytes.

  • Every schema publishes an explicit covered-field list; transient transport fields, signatures and the digest field itself are excluded.
  • TOML Project Agent manifests are parsed into the legion.project-agent.v1 semantic object before canonicalization; raw whitespace/comment changes do not change the semantic digest, while any policy/ability/instruction reference does.
  • Raw artifacts use SHA-256 over exact bytes and are never confused with structured-object digests.
  • knowledge_snapshot_sha256 covers only the sorted namespace revision vector and sorted active assertion id,digest,status,trust tuples. Its published empty fixture covers {"revisions":{},"assertions":[]}; it never includes local facts.
  • context_pack_sha256 separately covers the Knowledge snapshot digest, tree/source revisions, included local-fact/assertion digests, omissions, conflicts, budgets and stage after local compilation.
  • Phase 0 ships cross-language golden fixtures; every adapter MUST reproduce the same canonical bytes and digest before it joins the contract suite.

Atomicity rule: every transition uses compare-and-set (CAS) against Job state version and, when an Attempt exists, Attempt number, device ID and fencing token. Job and Attempt updates commit in one transaction using database server time. Attempt terminality does not always mean Job terminality: a clarification Attempt may complete while the Job waits for the user; a pre-effect Attempt may resume/release while its Job remains queued; only an effect-journaled execute Attempt’s verified terminal result settles the Job (review_ready for code-changing work, succeeded for read-only work). Attempt-only expired is transitional. Reconciliation reads effect_journaled_at: pre-effect reconciliation can only resume to acknowledged or end released|blocked|cancelled|abandoned; effectful reconciliation may resume execution/upload or settle from durable evidence. A terminal execution Job never gains another Attempt; explicit retry creates a new linked Job.

Execution sequence
  1. Local binding validates the repo-owned Project Agent manifest, computes its digest and publishes only user-approved safe metadata. The user creates a cloud session against that approved version.
  2. User submits a message. If no confirmed Spec exists, cloud queues a clarification Attempt pinned to the Session’s binding/Project Agent version, policy and either the active canonical Ledger revision vector/snapshot digest or the shared empty-snapshot fixture.
  3. Worker claims, commits payload/fencing/lease token to synchronous=FULL SQLite, durably commits, then acknowledges. If acknowledgement fails, the durable local claim is reconciled before any new claim.
  4. Worker builds a bounded Context Pack from local Project Agent/repository facts and, only when enabled, approved Ledger assertions. Deterministic completeness runs before Opus. Questions return to the Session; each answer creates a new immutable draft; the user confirms one exact version/digest.
  5. Cloud queues execution. Worker verifies device/binding, repository identity, manifest digest at the pinned commit, policy/profile/Legion version, Knowledge snapshot, cancellation and allowed base. Identity/schema/policy/digest drift blocks before effects; cancellation settles without effects. If the approved Provider/model or selected Capacity is temporarily unavailable, the Worker releases pre-effect and atomically sets state_reason=waiting_provider|waiting_capacity, waiting_since and jittered not_before; claim queries cannot return it before that time. Backoff grows to a configured cap but never beyond waiting_deadline_at.
  6. Worker resolves and pins the base SHA once, creates a dedicated outer worktree, writes the confirmed spec/context references to private files, and invokes the entire legion-run lifecycle beneath legion-process-supervisor.py. On macOS it applies the run-unique inherited Seatbelt fingerprint and canaries; Linux uses the proven pidfd/process-group path.
  7. Existing plan, routing, fan-out, validation, review, evaluation, evidence and learning run locally. Worker emits only bounded state transitions—not token streams.
  8. Worker atomically commits terminal result digest plus safe result/outbox event in one SQLite transaction before upload. Cloud verifies artifact receipts and result digest in one terminalization transaction. Code-changing success maps to review_ready.
  9. User later reviews/applies locally through existing digest-guarded control. Cloud MVP has no apply endpoint.
Lease, durable ordering and retry rules
  • Initial tuning Long poll up to 25 seconds, lease 90 seconds and heartbeat 20 seconds. The Worker owner MUST replace or confirm these values from Slice 9 load, pause and crash evidence before live execution.
  • Claims use one Postgres transaction with SKIP LOCKED, not_before <= database_now and NOT EXISTS any active leased|acknowledged|running|uploading|expired|reconciling Attempt. Database server time alone decides eligibility/expiry.
  • The Cloud Hub runs a bounded deadline sweeper; the claim transaction repeats the same CAS guard so an expired waiting_* Job becomes terminal blocked before it can lease even if the sweeper is delayed.
  • Temporary Provider/Capacity waiting uses persisted full-jitter exponential not_before backoff, capped by policy and waiting_deadline_at; release cannot create a tight claim/release loop.
  • Heartbeat runs outside the provider child process so a blocked model/tool call cannot silently stop renewal; failure to renew makes the cloud state expired → reconciling.
  • Durable order is fixed: cloud lease commit → local SQLite claim commit → cloud acknowledgement → effect journal entry → supervised execution → local evidence commit → local result/outbox commit → artifact upload → cloud terminalization transaction → local acknowledgement/cleanup.
  • Attempt updates compare current state, Attempt number, device ID and fencing token.
  • Lease loss during execution moves to reconciling; it never launches a second effectful Attempt blindly.
  • The same device may resume when local payload/result digest and fencing token match; otherwise the Job blocks for explicit recovery or retry as a new Job.
  • Network/408/425/429/5xx retry with full-jitter exponential backoff, honoring a bounded Retry-After, starting near one second and capped at five minutes.
  • Auth, schema, policy, digest conflict, non-idempotent 4xx and ambiguous external effects do not auto-retry.

20. MVP security, privacy and recovery

Authentication

Browser OIDC Authorization Code with PKCE, state and nonce; Secure, HttpOnly, SameSite session cookies with CSRF/origin protection; device authorization for CLI/Worker; short access tokens; rotated hashed refresh tokens in the OS keychain/secret store. Worker tokens are scoped to user, device and approved bindings.

Authorization

Deny by default. Every object lookup and state change checks authenticated owner, device, binding, Project Agent and action in one guarded query/transition. Opaque IDs and repository identity never grant access. Revocation is checked on claim, heartbeat, event and result upload.

Secret separation

Remove cloud tokens/KMS material before provider spawn; build cloud HTTP environment without provider secrets; provider auth stays in its existing local store.

Encrypted content

TLS and managed Postgres encryption are mandatory. User message/spec/result text uses envelope encryption before an external pilot: deployment-owned KMS key, versioned key ID, AAD binding owner/table/record, rotation by data-key rewrap, tested KMS-outage behavior and backup expiry.

Safe projection

Field allowlist, size bounds, secret/private-key/token/path/control-character scans and user authorization. Rejected items remain local with a visible reason.

Input, output, egress and supply chain

Reject unknown schema fields; use parameterized SQL and argument arrays rather than shell interpolation; allowlist Worker egress and context-source hosts; cap request, event and artifact sizes. The UI escapes all content, permits no raw model HTML and ships a restrictive CSP/security headers. Production Worker release artifacts and migration bundles are digest-pinned, signed and verified before use; dependency and secret scans gate release.

Project and knowledge isolation

Namespace filtering happens before ranking/decryption. MVP Project Agents read only personal plus their bound repository namespace; cross-project grants do not exist yet. Manifest widening changes the digest and requires explicit approval.

Cancellation

Cloud sets cancel_requested. Worker observes it; the full lifecycle already runs under the descendant-aware supervisor. macOS requires the inherited Seatbelt fingerprint plus both supervisor canaries; Linux requires the supported pidfd/process identity path. Any unavailable identity inspection fails closed. Cloud never sends a process signal.

Deletion

MVP is one personal/single-tenant deployment, so no cross-user sharing exists. Deletion appends a protected tombstone revision that every device cache/outbox must acknowledge; late uploads for the deleted session are rejected. After dependent jobs settle, cloud deletes message/spec ciphertext, removes it from snapshots and lets encrypted backups expire under documented retention. Audit keeps only non-content identifiers/reasons.

21. MVP performance and optimization plan

Optimization principle

The two-model xhigh policy is intentionally expensive. Performance comes from eliminating unnecessary model calls and infrastructure work—not reducing reasoning quality or skipping proof.

Before model calls

  • Deterministic completeness and schema checks.
  • Repository policy/Git/diagnostic discovery.
  • Changed-scope and cheapest-failure-first test selection.
  • Provider readiness cached by version/config digest.

Context

  • Latest immutable Spec and unanswered messages—not full chat.
  • Bounded active assertions and task-relevant local facts.
  • Cache by Project Agent, tree SHA, Spec, policy, Ledger snapshot digest and stage.
  • No whole-repo, whole-Ledger or whole-conversation prompt.

Execution

  • One plan per immutable spec/base/policy.
  • Dependency-aware fan-out only for ready independent work.
  • Safe dependency caches keyed by lockfile/runtime.
  • Skip unchanged validation/review fingerprints.

Cloud path

  • Long polling, batched progress and ledger events.
  • ETag/revision snapshot reads and incremental assertion tails.
  • Postgres indexes for claim, agent version and namespace revision paths.
  • No token streaming or synchronous upload on local hot path.

Storage

  • Append-only bounded files locally.
  • Content-addressed artifacts and dedupe.
  • Retention from day one.
  • No object store/broker until measured need.

Operations

  • Backpressure by worker/account.
  • Reserve capacity for independent review later.
  • Measure queue, startup, model, validation and approval separately.
  • Never optimize aggregate latency by hiding failed gates.

Measurement protocol

Every result records the exact command, seed, corpus/digest, baseline artifact, Git/Legion/agent/model-policy versions, hardware/OS, region, database class, cold/warm state, durability mode, data sizes, Worker count and concurrency. Microbenchmarks use at least 10 untimed warm-ups and 1,000 timed operations before reporting p99, with uncertainty reported. End-to-end comparisons use at least 30 paired case-runs at the same commit/agent/model/policy; every exclusion and infrastructure failure is reported, and p99 is omitted until the sample supports it. Stable deterministic suites repeat three times. Report only supported quantiles, plus queue, model, validation, upload, tokens and cost separately.
